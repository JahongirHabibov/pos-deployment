# POS-система — Руководство по развёртыванию в продакшн

Развёртывание этой системы рассчитано на полностью автоматическую установку через GUI-инсталлятор.
Ручной вариант нужен только как резервный и кратко описан в конце.

---

## POS-терминал: порядок установки

POS-терминал — это машина с Debian 13, которая загружается сразу в POS:

```
Debian 13 (trixie)
├── LightDM ── автовход «pos» ──► Openbox ──► Chromium --kiosk http://localhost[:PORT]
│          └─ экран входа ──────► LXQt (администратор, только для аварийных случаев)
├── Docker CE + Compose ──► frontend (nginx) · backend (FastAPI) · PostgreSQL · Redis
│                           image-service · updater · backup   (restart: unless-stopped)
└── systemd: watchdog контейнеров · синхронизация времени · агент выключения · диагностика
```

1. Установить Debian 13 с LXQt и учётной записью администратора (с sudo),
   клонировать этот репозиторий. Устанавливать с доступом к сети (зеркало
   пакетов и `trixie-security`, обновления Chromium приходят только оттуда) и
   выбрать часовой пояс ресторана: чеки печатаются по времени хоста.
2. Подготовить машину (обновление системы, киоск, Docker, защита от отключения питания):
   ```bash
   sudo ./host-setup/setup.sh
   sudo reboot
   ```
   Если при установке Debian был задан пароль root, `sudo` отсутствует:
   выполните `su -`, затем `<repo>/host-setup/setup.sh --admin-user <имя>`.
   Скрипт установит `sudo` и добавит в него администратора. Без сети или без
   зеркала Debian он остановится с сообщением, что нужно исправить; повторный
   запуск продолжит с места остановки.
3. На экране киоска нажать `Ctrl+Alt+Shift+A`, войти как администратор (LXQt)
   и запустить `./start-installer.sh` (см. ниже). На шаге 3 отметить агент
   выключения, диагностику и резервное копирование на USB.
4. Выйти из сеанса и выбрать пользователя киоска: POS откроется на весь экран.

- **URL:** киоск всегда открывает `http://localhost[:POS_PUBLIC_PORT]`, никогда
  `127.0.0.1`. Агент выключения принимает только этот origin, а хранилище
  браузера (идентификатор устройства) привязано к origin.
- **Сеть:** `POS_PUBLIC_PORT` намеренно опубликован на всех интерфейсах, чтобы
  устройства официантов открывали POS по `http://<ip-терминала>[:PORT]`.
- **Восстановление:** Chromium перезапускает systemd, контейнеры — Docker
  (`unless-stopped`), а зависшие (unhealthy) — watchdog.
- **SSH:** вход только по ключу. Перед запуском подготовки хоста через SSH
  добавьте ключ (`ssh-copy-id`), иначе скрипт откажется работать.

Подробности, сочетания клавиш и ручной чек-лист прошивки:
[`host-setup/README.md`](host-setup/README.md) (на английском).

## Рекомендуемый путь: полностью автоматическая установка (`installer.py`)

Запускайте через скрипт-лаунчер:

```bash
chmod +x start-installer.sh
./start-installer.sh
```

Опционально, для быстрого повторного деплоя:

```bash
./start-installer.sh --skip-setup
```

Что `start-installer.sh` делает перед запуском GUI:
- Обновляет этот репозиторий до последней версии (`git pull --ff-only`) и
  перезапускается; без сети продолжает с локальной версией.
- Проверяет наличие Python 3.10+.
- Проверяет наличие модуля `tkinter`.
- Проверяет, что `installer.py` существует в том же каталоге.
- Останавливается, если нет Docker или плагина Compose.
- Запускает мастер и передаёт ему аргументы CLI (включая `--skip-setup`).

## Предварительные требования

- Linux-машина с Docker и Docker Compose. Для POS-терминала: Debian 13,
  подготовленный через `host-setup/` (см. выше). Минимальное железо: 4 ГБ ОЗУ,
  диск 64 ГБ, Intel Core i3 (4-го поколения).
Необходимые входные данные от разработчика/дистрибьютора или администратора Legisell:
- Одноразовый токен провизии (OTPK).
- URL бэкенда Legisell.
- Имя пользователя GHCR и токен (read:packages).
- Теги Docker-образов (`IMAGE_*`).

Примечания:
- Если `.env` уже существует, релевантные поля заполняются автоматически.
- Последние теги релизов читаются из `manifest.json` в `DEPLOYMENT_REPO` и
  подставляются в поля `IMAGE_*`; изменённые строки подсвечиваются. Если
  запрос не удался, в блоке указывается причина (неверный репозиторий,
  HTTP-статус, нет сети).

### Шаг 2 — Docker Login

| Поле | Назначение |
|---|---|
| GHCR Login уже выполнен (чекбокс) | Пропускает `docker login`, если учётные данные GHCR уже есть в `~/.docker`. |
| Пользователь GHCR | Используется в `docker login ghcr.io`. |
| Токен GHCR / PAT | Используется как пароль реестра (`read:packages`). |
| Sudo-пароль | Нужен для выполнения Docker-команд через `sudo`. |
| Показать токен / пароль (чекбоксы) | Только переключение видимости, значения не меняют. |

Примечания:
- При успешном входе создаётся `~/.docker/pos-auth.json` для GHCR-пулла образов обновлятором.
- Инсталлятор записывает `POS_DOCKER_AUTH_FILE` в `.env` с абсолютным Linux-путём к этому файлу.
- GUI не показывает это поле для ручного ввода; это техническое значение управляется инсталлятором.
- Compose больше не создаёт этот путь автоматически; если файл отсутствует или является папкой, повторите Docker Login в инсталляторе.
- Служба резервного копирования не имеет отдельного логина и опубликованного порта — управляется из админ-панели POS (Настройки ▸ Резервные копии), с правом `system.backup`.

### Шаг 3 — Развёртывание

| Поле | Назначение |
|---|---|
| Sudo-пароль (условно) | Появляется только если sudo-пароль не был получен на шаге 2/из состояния. Нужен для финальных Docker-операций. |
| Показать пароль (чекбокс) | Только переключение видимости. |
| Установить агент выключения (чекбокс) | Ставит `kiosk-agent/` как systemd-сервис на эту машину, чтобы экран входа в POS мог её выключить. По умолчанию выключен; выбор сохраняется в `.env` как `POS_KIOSK_AGENT` и подставляется при следующем запуске. В режиме WSL 2 скрыт. См. раздел «Агент выключения (kiosk power agent)» ниже. |
| Настроить автомонтирование USB (чекбокс) | Ставит `usb-backup/` (правило udev), чтобы подключённую USB-флешку можно было использовать как дополнительное место хранения резервных копий. По умолчанию выключен; сохраняется в `.env` как `POS_USB_BACKUP`. В режиме WSL 2 скрыт. См. раздел «Резервные копии на USB» ниже. |

На этом шаге также показывается сводка только для чтения (API URL, GHCR user, app/port/db/image значения) и live-лог развёртывания.

## Что автоматизирует инсталлятор

- Вызывает `provision.py` и создаёт/обновляет `.env`.
- Патчит ключи деплоя в `.env` (`IMAGE_*`, `DEPLOYMENT_REPO`, `HOST_COMPOSE_PROJECT_DIR`).
- Выполняет GHCR login и сохраняет bridge-файл учётных данных для обновлятора.
- Сеть `pos-network` создаётся автоматически через Docker Compose на основе `docker-compose.prod.yml` — отдельный шаг создания не требуется.
- Запускает `docker compose pull` с индикатором прогресса (вывод буферизуется внутри, построчный лог не отображается) и `docker compose up -d` с live-логом.
- Включает синхронизацию времени и записывает часовой пояс хоста (`TZ`) в `.env`.
- Определяет тип диска и объём ОЗУ и записывает профиль базы данных (`PG_*`) в
  `.env` (см. ниже).
- Однократно создаёт служебный токен обновлятора (`UPDATER_API_TOKEN`) (см.
  «Эксплуатация и обслуживание»).
- Сохраняет лог развёртывания в `logs/deploy-<timestamp>.log`.

## Аппаратный профиль базы данных

PostgreSQL нужны разные настройки на жёстком диске и на SSD, на 4 ГБ и на 8 ГБ
ОЗУ. При каждом развёртывании инсталлятор запускает `host_profile.py`: он
прослеживает устройство `/var/lib/docker` до физического диска (раздел, LVM,
dm-crypt; один вращающийся диск в цепочке — значит HDD) и читает `MemTotal`.
Результат записывается в `.env`:

| Ключ | HDD | SSD |
|---|---|---|
| `PG_RANDOM_PAGE_COST` | 4 | 1.1 |
| `PG_EFFECTIVE_IO_CONCURRENCY` | 2 | 200 |

| Ключ | меньше 6 ГиБ ОЗУ (`4g`) | 6 ГиБ и больше (`8g`) |
|---|---|---|
| `PG_SHARED_BUFFERS` | 256MB | 512MB |
| `PG_EFFECTIVE_CACHE_SIZE` | 1GB | 2GB |
| `PG_WORK_MEM` | 4MB | 8MB |
| `PG_MAINTENANCE_WORK_MEM` | 64MB | 128MB |

- `POS_HOST_PROFILE` содержит имя результата: `hdd-4g`, `hdd-8g`, `ssd-4g` или
  `ssd-8g`.
- Если определить не удалось, используются значения HDD/4 ГБ. Те же значения
  стоят по умолчанию в compose-файле, так что машина без профиля тоже в
  безопасности.
- `POS_HOST_PROFILE=manual` сохраняет вручную изменённые значения `PG_*`.
- Проверить определение: `python3 host_profile.py`.
- Изменённое значение один раз пересоздаёт контейнер базы данных при следующем
  `docker compose up -d` (несколько секунд простоя).
- `wal_compression` всегда включён. `fsync`, `full_page_writes` и
  `synchronous_commit` остаются на безопасных значениях по умолчанию —
  подтверждённые данные переживают отключение питания.
- Существующие установки: `git pull`, затем повторно запустить инсталлятор
  (`./start-installer.sh --skip-setup`). Обновления через админ-панель
  доставляют только образы, но не compose-файл.

## Резервные копии на USB

Резервные копии по умолчанию хранятся только в `backups/` на этой машине.
USB-флешку можно зарегистрировать как дополнительную цель — тогда каждая копия
базы и изображений пишется в оба места.

Почему нужна часть на хосте: служба резервного копирования — это контейнер, а
контейнер не может смонтировать блочное устройство. Флешку монтирует хост,
compose лишь делает этот монтаж видимым (`/external/*`, с распространением
`rslave` — без него флешка, вставленная после запуска контейнера, останется
невидимой). На машине с сеансом рабочего стола udisks монтирует флешки в
`/media/<user>/<LABEL>`, и ничего дополнительно не нужно. В сеансе киоска нет
файлового менеджера, который делал бы это, поэтому правило udev из
`usb-backup/` монтирует их в `/mnt/kassio-usb/by-uuid/<UUID>`.

Настройка:

1. Отметить «Настроить автомонтирование USB» на шаге 3 (или вручную
   `sudo usb-backup/install.sh`).
2. `docker compose up -d backup` — привязки `/external` заданы в compose-файле,
   поэтому на существующей установке сначала нужен `git pull`.
3. POS ▸ Настройки ▸ Резервное копирование ▸ Внешние цели ▸ Добавить цель.

Флешку вставлять в **Docker-хост**, а не в терминал-тонкий клиент. Если во время
резервного копирования цель не подключена, копия всё равно создаётся успешно, а
цель помечается как неудачная — вынутая флешка никогда не срывает ночную копию.
Подробности: `usb-backup/README.md`.

## Агент выключения (kiosk power agent)

Киоск-терминал (`host-setup/`) загружается сразу в браузер без рабочего стола: ни окон, ни меню
выключения. Персонал не может выключить такое устройство. JavaScript в браузере
выключить машину не может, а бэкенд не должен: в смешанных установках он
работает на сервере, тогда как пользователь стоит перед другим терминалом —
выключился бы не тот компьютер.

`kiosk-agent/` закрывает этот пробел: HTTP-сервис только на `127.0.0.1:9110`,
устанавливаемый на каждую машину. Экран входа в POS опрашивает его и показывает
кнопку выключения только там, где он отвечает. Сервис работает под root через
systemd — именно поэтому выключение проходит без пароля sudo и без запроса
polkit.

- **На этом Docker-хосте:** отметьте «Установить агент выключения» на шаге 3.
  Инсталлятор запустит `kiosk-agent/install.sh` с уже введённым паролем sudo и
  ограничит допустимый origin локальным адресом POS.
- **На терминалах без этого репозитория** (устройства только с браузером):
  выполните там вручную `sudo kiosk-agent/install.sh --origins http://<pos-url>`
  или включите агент в образ киоска.
- **На сервере в стойке:** не отмечайте. Больше ничего не меняется.

Неудачная установка агента никогда не проваливает развёртывание — POS просто не
покажет кнопку выключения. Подробности, API и модель безопасности:
`kiosk-agent/README.md`.

## Эксплуатация и обслуживание

### Требования и принятые риски

- **Сеть:** POS работает по обычному HTTP. Терминалы и устройства официантов
  должны находиться в отдельной кассовой Wi-Fi/LAN (WPA2/WPA3, надёжный ключ,
  без гостевых устройств). Терминалы находятся за NAT и недоступны из интернета.
- **Межсетевой экран:** скрипты его не настраивают; при необходимости — вручную.
  Docker публикует `POS_PUBLIC_PORT` в обход входящих правил ufw/nftables, так
  что межсетевой экран хоста этот порт не закроет (он и должен быть открыт).
- **Пока принято:** без шифрования диска и резервных копий, без пароля GRUB.
  Украденное устройство раскрывает свои данные и `.env`.

### Обновления

- **POS:** из админ-панели (Настройки ▸ Обновление системы). Доставляются только
  образы; изменения этого репозитория требуют `git pull` и
  `./start-installer.sh --skip-setup`.
- **Операционная система:** вручную, когда администратор на месте:
  ```bash
  sudo apt update && sudo apt upgrade        # Docker остаётся зафиксированным
  sudo apt-mark unhold docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
  sudo apt install --only-upgrade docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
  sudo apt-mark hold docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
  ```
  Docker обновлять только вне часов работы: контейнеры перезапускаются.
- **После обновления Chromium:** нажать `Ctrl+Alt+Shift+R` (или перезагрузить).
  Запущенный Chromium, файлы которого заменены, роняет страницы.

### Служебный токен обновлятора

Обновлятор управляет Docker, поэтому принимает запросы только от бэкенда.
Инсталлятор при первом развёртывании создаёт `UPDATER_API_TOKEN` в `.env`;
compose передаёт его бэкенду (он его отправляет) и обновлятору (он его
проверяет). Администраторы работают в админ-панели как раньше.

- `UPDATER_REQUIRE_TOKEN=false` (по умолчанию): неверный токен отклоняется,
  отсутствующий пока принимается — терминал со старым образом бэкенда
  продолжает работать.
- `UPDATER_REQUIRE_TOKEN=true`: запросы без токена тоже отклоняются.
  Включать только когда терминал работает с образом бэкенда, который
  отправляет токен.
- Значение никому не передавать и не выводить; чтобы заменить, удалить строку
  и снова запустить инсталлятор.

### Краткая инструкция для персонала

| Ситуация | Что делать |
|---|---|
| Запуск длится до 2 минут (чёрный экран) | Ждать; не выключать. |
| Страница показывает «Опаньки…» / «Aw, Snap!» | Нажать **Перезагрузить** или `Ctrl+Alt+Shift+R`. |
| Экран входа вместо POS | Нажать на пользователя киоска (без пароля). |
| Устройство зависло | Удерживать кнопку питания 5 с, затем включить. |
| Выключение в конце дня | Кнопка выключения на экране входа POS или короткое нажатие кнопки питания. |

Администраторам: по окончании работы выйти из сеанса LXQt, иначе он остаётся
открытым на экране.

## Ручная установка (краткий резервный сценарий)

Используйте только если GUI недоступен.

1. Выполните вход в GHCR:

```bash
export GHCR_USER="<ваш-ghcr-пользователь>"
export GHCR_TOKEN="<ваш-ghcr-readonly-токен>"
echo "$GHCR_TOKEN" | sudo docker login ghcr.io -u "$GHCR_USER" --password-stdin
python3 -c 'import base64,json,os,pathlib; p=pathlib.Path.home()/".docker"/"pos-auth.json"; p.parent.mkdir(parents=True, exist_ok=True); p.write_text(json.dumps({"auths":{"ghcr.io":{"auth":base64.b64encode((os.environ["GHCR_USER"]+":"+os.environ["GHCR_TOKEN"]).encode()).decode()}}}, indent=2)+"\n"); p.chmod(0o600)'
```

Файл `pos-auth.json` — это bridge-файл для обновлятора в WSL/Docker Desktop. Он должен быть обычным файлом, а не папкой.

2. Выполните провизию `.env`:

```bash
python3 provision.py --token <ONE_TIME_PROVISIONING_TOKEN> --api-url <LEGISELL_BACKEND_URL>
```

3. Проверьте, что в `.env` корректны минимум эти значения:

```dotenv
IMAGE_BACKEND=ghcr.io/<org>/pos-backend:<tag>
IMAGE_FRONTEND=ghcr.io/<org>/pos-frontend:<tag>
IMAGE_IMAGE_SERVICE=ghcr.io/<org>/pos-image-service:<tag>
IMAGE_UPDATER=ghcr.io/<org>/pos-updater:<tag>
IMAGE_BACKUP=ghcr.io/<org>/pos-backup:<tag>
DEPLOYMENT_REPO=<org>/pos-deployment
HOST_COMPOSE_PROJECT_DIR=/absolute/path/to/pos-deployment
POS_DOCKER_AUTH_FILE=/home/<user>/.docker/pos-auth.json
```

Часовой пояс и учётная запись администратора задаются позже в браузере через мастер первичной настройки.

Необязательно: добавьте профиль базы данных, который выводит
`python3 host_profile.py` (без него действуют значения HDD/4 ГБ).

Для `POS_DOCKER_AUTH_FILE` используйте абсолютный Linux-путь; не используйте `~` в `.env`. При установке через GUI это значение записывает сам инсталлятор.

4. Запустите сервисы:

```bash
sudo docker network create --driver bridge pos-network || true
sudo docker compose -f docker-compose.prod.yml pull
sudo docker compose -f docker-compose.prod.yml up -d
```

5. Проверьте состояние:

```bash
sudo docker compose -f docker-compose.prod.yml ps
sudo docker compose -f docker-compose.prod.yml logs -f
```
